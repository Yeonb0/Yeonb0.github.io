## 이번 Phase의 목표

[이전 글](/devlog/factory-game-phase-0/)에서 저장소 뼈대를 만들었다. 게임 규칙을 담당하는 순수 C# 라이브러리 (core), 테스트, Godot 프로젝트를 하나로 묶고, Godot 없이도 테스트가 돌아가게 했다.

이번부터는 게임의 심장인 **공정 코어**를 만든다. 공정 코어는 "기계에 어떤 부품을 어떤 순서로 넣었을 때, 들어간 재료가 무엇이 되어 나오는가"를 계산하는 부분이다. 작업이 커서 세 편으로 나눴고, 이번 글은 그 첫 단계인 **데이터 로더**다.

게임 규칙은 코드에 직접 쓰지 않고 JSON 파일 (사람도 읽을 수 있는 데이터 형식)에 적어 둔다. 예를 들어 "청동은 950 °C에서 녹는다", "피스톤은 판재를 누른다" 같은 내용이다. 데이터 로더는 이 JSON 파일들을 읽어서, 코드가 "청동의 녹는점은?"이라고 물으면 바로 답할 수 있는 형태로 만들어 두는 일을 한다.

완료 기준은 셋이었다.

1. 데이터 JSON 4개와 골든 테스트 65개를 넣는다 (처음엔 전부 실패하는 상태로)
2. 아이템 상태 · JSON 구조 · 로더를 C#으로 만든다
3. JSON의 값이 정확히 읽히는지 확인하는 로더 테스트 7개를 통과한다

## 계획

공정 코어 전체는 다섯 단계로 나눴다.

| 단계 | 내용 | 이번 글 |
|---|---|---|
| P1-1 | 데이터 JSON (물성 · 변환 규칙 · 부품 · 외피) | ✓ |
| P1-2 | 골든 테스트 (처음엔 전부 빨간불) | ✓ |
| P1-3 | 아이템 상태 · 데이터 로더 | ✓ |
| P1-4 | ProcessResolver (규칙 판정) | 다음 글 |
| P1-5 | 배치 규칙 · 설계 검사 | 그다음 글 |

순서에 이유가 있다. **테스트를 먼저 만들고, 그 테스트를 통과하는 코드를 나중에 쓴다.** 골든 테스트는 "이 입력이면 반드시 이 결과가 나와야 한다"는 정답표다. 예를 들어 "철광석에 연소실 두 개를 지나게 하면 1000 °C의 연철 덩어리가 된다", "피스톤을 연소실보다 앞에 두면 첫 칸에서 실패한다" 같은 65개 사례가 들어 있다. 이 정답표는 설계 단계에서 Python으로 검증해 둔 규칙에서 만들었다. 그래서 내가 C#으로 다시 구현하면서 실수하면 테스트가 바로 알려 준다.

이번 단계가 끝나도 골든 테스트는 여전히 전부 실패한다. 데이터를 읽는 것까지만 했기 때문이다. 대신 로더 테스트로 "데이터는 정확히 읽힌다"를 먼저 확인한다.

## 결정과 이유

### 아이템 상태와 데이터 정의는 다른 종류의 타입으로

C#에는 데이터를 담는 타입이 여러 가지 있다. 여기서는 둘을 골라 썼다.

| | 아이템 상태 (`ItemState`) | 데이터 정의 (`Material` 등) |
|---|---|---|
| 담는 것 | "지금 기계 안에 있는 이 물건" : 물질 · 형태 · 온도 | "청동이란 무엇인가" : 녹는점 · 경도 · 가공 온도 범위 |
| 어디서 오나 | 게임이 실행 중에 만들고 바꿈 | JSON에서 한 번 읽음 |
| 고른 타입 | `readonly record struct` (작은 값, 복사해서 넘김) | `sealed record` (큰 데이터, 참조로 공유) |

아이템 상태는 값이 세 개뿐이고, 나중에 벨트 위 아이템 수백 개가 들고 다닌다. 그래서 C의 구조체처럼 값 자체를 복사하는 `struct`가 맞다. 반대로 물질 정의는 필드가 열 개가 넘고 목록 · 표를 품고 있으며, 게임 시작 때 한 번 읽어 여러 곳에서 같이 쓴다. 이걸 `struct`로 두면 넘길 때마다 큰 복사본이 생긴다.

두 타입 모두 **불변** (만든 뒤 값을 바꿀 수 없음)이다. 아이템 온도가 바뀌면 기존 값을 고치는 대신 온도만 바뀐 새 값을 만든다. 같은 입력이면 항상 같은 결과가 나와야 하는 게임이라, 값이 몰래 바뀌는 길을 처음부터 막아 두었다.

### "없음"과 "비어 있음"을 구분한다

물질 데이터의 `coldForms` (상온에서 가공할 수 있는 형태 목록)는 값이 세 종류다.

- `null` : 제한 없음 (모든 형태 허용)
- `[]` : 빈 목록 (아무것도 허용 안 함, 예 : 광석)
- `["plate", "rod", …]` : 목록에 있는 것만 허용

`null`과 `[]`를 같은 것으로 취급하면 규칙이 정반대로 뒤집힌다. 그래서 C# 타입을 `List<string>?` (목록 자체가 없을 수 있음)로 정했다. 비슷해 보이는 `List<string?>` (목록은 있는데 원소가 비어 있을 수 있음)과는 뜻이 다르다. 물음표 하나의 위치가 규칙을 바꾼다.

### 키가 정해져 있으면 record, 데이터가 키를 정하면 Dictionary

JSON 객체를 C#으로 받는 방법은 두 가지다.

- 외피의 포트 수 `{ "input": 1, "output": 1, "fuel": 1 }` : 키가 항상 이 셋이다 → 전용 타입 (`record`)
- 변환 규칙 `{ "press": { "ingot": "plate", … }, "cut": { … } }` : 동사 · 형태 이름은 데이터가 정한다 → 사전형 (`Dictionary`)

기준은 "키 이름이 코드의 일부인가, 데이터의 일부인가"다. 변환 규칙을 전용 타입으로 만들면, 새 동사를 JSON에 추가할 때마다 C# 코드도 고쳐야 한다. 이 프로젝트는 "규칙은 데이터로 구동한다"를 원칙으로 두고 있어서 사전형으로 받았다. 반대로 고정된 키는 전용 타입으로 받아야 오타를 컴파일러가 잡아 준다.

### 로더는 파일 위치를 모른다

데이터 묶음 `GameData`는 `GameData.Load(폴더 경로)` 하나로만 만들 수 있게 했다. 생성자를 외부에 공개하지 않아서, "반드시 파일에서 읽어서만 만들어진다"를 컴파일러가 보장한다. 그리고 폴더 경로는 항상 밖에서 받는다. 테스트는 테스트 출력 폴더를, Godot는 게임 폴더를 넘기면 된다. 같은 코드가 테스트 · 게임 · CI 어디서나 그대로 동작한다.

### 같은 기간 설계 쪽에서 정한 것

구현과 나란히 설계 대화에서도 몇 가지를 정했다. 이번 Phase 코드에는 아직 들어가지 않았지만, 다음 단계들이 이 결정 위에 선다.

- **처리 시간은 파이프라인으로** : 기계의 처리량은 가장 느린 슬롯이 정하고, 한 개가 통과하는 시간은 슬롯 시간의 합이다. 두 기계를 한 외피로 합쳤을 때 처리량이 반으로 떨어지면 "작은 기계 여러 대 → 큰 기계 한 대로 통합"하는 재미를 벌하게 되기 때문이다.
- **레시피 뷰어 · 물질 도감을 MVP에 포함** : 실패 사유가 "온도 범위 밖" 같은 물성을 언급하므로, 그 물성을 바로 확인할 곳이 필요했다. 가공 순서는 직접 만들어 본 것만 보여 줘서 발견하는 재미는 남긴다.

## 구현

파일 구성은 이렇다.

```text
core/
  Model/   ItemState, 물질 · 부품 · 규칙 · 외피 record
  Data/    GameData (로더)
data/      materials · parts · rules · shells .json
tests/
  Golden/        골든 테스트 65개 + 연결부 (GoldenHarness)
  LoaderTests    로더 테스트 7개
```

아이템 상태는 이 한 선언이 전부다. `record`를 쓰면 C#이 읽기 전용 속성 · 생성자 · 값 비교 · 복사 기능을 자동으로 만들어 준다.

{% raw %}
```csharp
public readonly record struct ItemState(
  string Material,
  string Form,
  int TempC
);
```
{% endraw %}

로더의 핵심은 파일 네 개를 같은 방식으로 읽고, 목록을 id로 찾는 표로 바꾸는 부분이다.

{% raw %}
```csharp
public static GameData Load(string dir)
{
  var materialFile = ReadFile<MaterialFile>(dir, "materials.json");
  var partFile = ReadFile<PartFile>(dir, "parts.json");
  // rules.json, shells.json도 같은 방식

  return new GameData(
    materials: materialFile.Materials.ToDictionary(m => m.Id),
    parts: partFile.Parts.ToDictionary(p => p.Id),
    /* … */);
}
```
{% endraw %}

`ReadFile<T>`는 결과 타입만 바꿔 네 번 쓰는 **제네릭 메서드**다 (C++의 템플릿, Java의 제네릭과 같다). `ToDictionary(m => m.Id)`는 목록을 돌면서 각 항목의 id를 열쇠로 삼는 표를 만든다. 이렇게 해 두면 다음 단계에서 `data.Materials["bronze"].MeltC`처럼 바로 찾을 수 있다.

JSON을 읽는 설정도 두 가지 필요했다. JSON 키는 `meltC`처럼 소문자로 시작하고 C# 속성은 `MeltC`처럼 대문자로 시작해서, **대소문자를 무시**하도록 했다. 그리고 부품 역할 `"heat"` 같은 문자열을 C#의 열거형 (정해진 값 목록) 으로 읽는 **변환기**를 붙였다.

## 막혔던 점

이번 Phase는 C#을 거의 처음 쓰면서 진행했다. 그래서 막힌 곳 대부분이 언어에 익숙하지 않아서 생긴 것이었다.

- **에러 없이 조용히 비는 값** : JSON 키 `port`를 C# 쪽에서 `Portm`으로 잘못 적었는데, 빌드도 되고 읽기도 성공했다. 대신 모든 부품의 포트 값이 비어서 들어왔다. `conditions`를 `Condition`으로 적었을 때도 같았다. JSON 읽기는 모르는 키를 그냥 무시하기 때문이다. 반대로 C# 코드 안의 오타는 컴파일러가 바로 잡아 준다. 이 차이 때문에 로더 테스트에서 "입력 포트의 값이 정말 `input`인가"처럼 **실제 값**을 확인하도록 했다.
- **괄호 모양이 타입을 정한다** : JSON의 `{ }` (객체)를 목록 타입으로 받으려 해서 읽기 예외가 났다. `[ ]`는 목록, 키가 고정된 `{ }`는 전용 타입, 키가 데이터인 `{ }`는 사전형이라고 정리했다.
- **필드와 속성** : `public int AmbientC;`라고 쓰면 밖에서 값을 바꿀 수 있는 필드가 된다. `{ get; }`을 붙여야 생성할 때만 정할 수 있는 읽기 전용 속성이 된다. 규칙 데이터가 실행 중에 바뀌면 안 되므로 전부 속성으로 바꿨다.
- **메서드는 클래스 안에만** : C · TS 습관대로 파일에 함수를 바로 쓰려 했다. C#은 Java처럼 모든 메서드가 클래스 안에 있어야 한다.
- **자동 완성이 몰래 넣는 using** : 편집기의 자동 완성이 쓰지도 않는 네임스페이스를 세 번이나 끼워 넣었다. 저장하기 전에 회색으로 흐려진 줄을 지우는 습관을 들였다.

## 결과와 배운 점

완료 기준 세 가지를 모두 채웠다. 테스트 결과는 **합계 73, 성공 8, 실패 65**였다.

- 성공 8 : 이전 Phase의 확인 테스트 1개 + 로더 테스트 7개
- 실패 65 : 골든 테스트 전부. 아직 규칙 판정을 만들지 않아서 "구현되지 않음" 예외로 실패하는 것이 정상이다

로더 테스트는 물질 9 · 부품 10개가 빠짐없이 읽히는지, 생고무의 경도 0.5 같은 소수가 정확한지, 청동과 철광석의 `coldForms`가 `null`과 `[]`로 구분되는지, 문자열 `"heat"`가 열거형으로 바뀌는지를 확인한다.

배운 것을 하나로 줄이면 이렇다. **타입을 고르는 일이 곧 규칙을 정하는 일이다.** 물음표 하나 (`List<string>?`)가 "제한 없음"과 "전부 금지"를 가르고, `record`냐 `Dictionary`냐가 "새 규칙을 추가할 때 코드를 고쳐야 하는가"를 가른다.

다음 글에서는 이 데이터를 써서 실제 규칙 판정, 즉 가열 · 굽기 · 가공과 실패 판정을 하는 `ProcessResolver`를 만든다. 골든 테스트가 하나씩 초록불로 바뀌는 단계다.
